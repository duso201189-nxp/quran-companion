# Provider Map — Qur'an Companion

Written after PR #19. Full reference catalog of every Riverpod provider
in Qur'an Companion, generated by reading all `*_providers.dart` files
plus every other file that declares a top-level `final xProvider = ...`
(screens/controllers that mix DI with UI state). 79 providers found
across 6 core infrastructure providers, 3 app-level providers, and 70
feature providers spanning 18 feature directories (`search/` and
`study/` currently declare none — see §3).

**How to read the tables**: `Type` gives the exact Riverpod provider
class plus modifiers (`.autoDispose`, `.family<Arg>`) as written in
source. `File` is relative to `lib/`.

## 2. Dependency graph (repository-backing providers)

All 14 `*RepositoryProvider`s that construct a `*RepositoryImpl`, plus
their `ref.watch` dependencies (constructor args only).

### 2.1 Leaf repositories (direct DB + logger dependency)

```
appDatabaseProvider (core)         — leaf, no provider deps (opens content DB)
userDatabaseProvider (core)        — leaf, no provider deps (opens user DB)
crashReporterProvider (core)       — leaf, no provider deps
loggerProvider (core)              — depends on: crashReporterProvider

quranRepositoryProvider (quran)              -> appDatabaseProvider, loggerProvider
lexiconRepositoryProvider (lexicon)          -> appDatabaseProvider, loggerProvider

userContentRepositoryProvider (quran)        -> userDatabaseProvider, loggerProvider
flashcardRepositoryProvider (flashcards)     -> userDatabaseProvider, loggerProvider
khatmCycleRepositoryProvider (khatm)         -> userDatabaseProvider, loggerProvider
bookmarkCollectionRepositoryProvider (library) -> userDatabaseProvider, loggerProvider
quizRepositoryProvider (quiz)                -> userDatabaseProvider, loggerProvider
studySessionRepositoryProvider (stats)       -> userDatabaseProvider, loggerProvider
schedulerRepositoryProvider (learning)       -> userDatabaseProvider, loggerProvider, schedulingAlgorithmProvider
                                                 (schedulingAlgorithmProvider is itself a leaf: Provider<SchedulingAlgorithm> = SM2SchedulingAlgorithm(), no deps)
```

`quranRepositoryProvider` / `lexiconRepositoryProvider` sit on the
**content** DB ("group A" — read-only Qur'an data). All the others sit
on the **user** DB ("group B" — per-user mutable state). This split is
a deliberate architecture line (two separate Drift databases,
`AppDatabase` vs `UserDatabase`), not an accident — see
`MASTER_ARCHITECTURE.md` §2.1.

### 2.2 The aggregation chain — Analytics → AI Tutor → Learning Journey → Smart Learning → Read Model

```
analyticsRepositoryProvider (analytics)
  -> schedulerRepositoryProvider (learning)
  -> flashcardRepositoryProvider (flashcards)
  -> lexiconRepositoryProvider (lexicon)
  -> studySessionRepositoryProvider (stats)
      (4 sibling leaf repositories — no DB access of its own)

aiTutorRepositoryProvider (ai_tutor)
  -> analyticsRepositoryProvider (analytics)
      (single dependency)

learningJourneyRepositoryProvider (learning_journey)
  -> aiTutorRepositoryProvider (ai_tutor)
      (single dependency)

smartLearningRepositoryProvider (smart_learning)
  -> learningJourneyRepositoryProvider (learning_journey)
      (single dependency)

learningSnapshotRepositoryProvider (read_model)
  -> smartLearningRepositoryProvider (smart_learning)
      (single dependency)
```

Each link in the chain follows the exact same shape (explicitly noted
in every file's doc comments as mirroring the previous one): **one
`Provider<Repository>` built from exactly the dependency(ies) already
available, plus `FutureProvider.autoDispose` wrappers that call
straight through to one repository method.** This means a single
"full" read at the bottom of the chain
(`learningSnapshotRepositoryProvider.getSnapshot()`, if actually
invoked) fans out to: 1 SmartLearning call → 1 LearningJourney call →
up to 3 AITutor calls → up to 4 Analytics calls each — i.e., up to ~12
Analytics-repository calls. This fan-out is exactly why the bypass
pattern in §2.3 exists.

### 2.3 Bypass pattern — reusing an upstream sibling provider's cache instead of re-walking the chain

Two providers deliberately skip their own repository layer and instead
reuse another **already-declared FutureProvider's** cached `.future`
value, applying the same pure function the repository implementation
uses internally:

**`dailyLearningPlanProvider`** (`learning_journey/data/learning_journey_providers.dart`):
```dart
final dailyLearningPlanProvider = FutureProvider.autoDispose<DailyLearningPlan>((ref) async {
  final suggestions = await ref.watch(tutorSuggestionsProvider.future);
  return computeDailyLearningPlan(suggestions, DateTime.now());
});
```
Instead of `ref.watch(learningJourneyRepositoryProvider).getDailyPlan()`
(which would trigger a brand-new `AITutorRepository.getSuggestions()`
call → 4 fresh Analytics calls every time it's watched), it reuses
`tutorSuggestionsProvider`'s cached result if some other screen (e.g.
`TutorHomeScreen`) is already keeping it alive. `computeDailyLearningPlan`
is the *exact* pure function `LearningJourneyRepositoryImpl.getDailyPlan()`
uses internally — no new logic, no skipped `AITutorRepository` calls,
just reuse of a result that may already exist.

**`learningSnapshotProvider`** (`read_model/data/learning_snapshot_providers.dart`):
```dart
final learningSnapshotProvider = FutureProvider.autoDispose<LearningSnapshot>((ref) async {
  final session = await ref.watch(smartLearningSessionProvider.future);
  return computeLearningSnapshot(session, DateTime.now());
});
```
Same pattern one level up the chain, and — per its doc comment — **the
single biggest savings point in the whole chain**: if
`smartLearningSessionProvider` is already alive (e.g.
`SmartLearningScreen` is open), this avoids the *entire* SmartLearning
→ LearningJourney → up-to-3×AITutor → up-to-12×Analytics fan-out
described in §2.2. `computeLearningSnapshot` is the exact pure function
`LearningSnapshotRepositoryImpl.getSnapshot()` uses internally.

**Why this is safe here but not applied everywhere**: both
`learningJourneyProvider` (one level below the repository it would
bypass) and the top of the read-model chain are explicitly *not* given
this optimization where a screen's pull-to-refresh/retry only
invalidates the *outer* provider and not the upstream one being reused
— doing so would let "pull to refresh" silently return stale cached
data (a correctness bug, not just a performance one). The two
providers that *do* bypass currently have no UI watching/refreshing
them, so that hazard doesn't yet apply — called out explicitly in both
files' doc comments as the reason it's safe *today*, implying it needs
revisiting if/when a screen is built for either (see
[PRODUCT_ROADMAP.md](../release/PRODUCT_ROADMAP.md) v1.1, "give Read
Model a real UI").

Both underlying repository-backed providers are intentionally kept,
unused on the hot path, purely to remain the standard DI access point
for their repository interface (tests, or any future non-Riverpod
consumer) — matching the project-wide convention that every repository
gets exactly one `*RepositoryProvider`.

### 2.4 Cross-repository "sync bridge" providers (distinct pattern — not a performance bypass)

Two `StreamProvider.autoDispose<void>` providers exist purely to
connect two repositories that are intentionally kept independent of
each other (no `ref.watch` between the repositories themselves — the
bridge lives one layer up, at the provider tier):

- **`schedulerSyncProvider`** (`learning/data/scheduler_providers.dart`):
  watches `userContentRepositoryProvider.watchAllReviewAyahs()`, calls
  `schedulerRepositoryProvider.syncWithReviewQueue(...)` on every
  emission. Lets `SchedulerRepository` (SM-2 scheduling) stay ignorant
  of `UserContentRepository` (bookmarks/review flags).
- **`flashcardSchedulerSyncProvider`** (`flashcards/data/flashcard_providers.dart`):
  watches `flashcardRepositoryProvider.watchAllFlashcards()`
  (lemma-type only), calls `schedulerRepositoryProvider.syncItemsForType(LearningItemType.lemma, ...)`
  on every emission. Lets `FlashcardRepository` stay ignorant of
  `SchedulerRepository`.

Both are `.autoDispose` and are watched as the first line of the
provider that needs "freshly synced" due-card data
(`dueReviewCardsProvider`, `dueFlashcardCardsProvider` respectively) —
i.e. they only run while something downstream actually needs due-card
data, not as a background always-on sync.

### 3.2 Cross-feature consumption — "if I touch file X, who else reads it"

Edges below are `consumer feature -> provider(s) it reads, owned by
producer feature`. Same-feature (`data/` reading its own
`presentation/`, etc.) is called out separately where it's
architecturally notable.

- **`ai_tutor/` -> `analytics/`**: `aiTutorRepositoryProvider` watches
  `analyticsRepositoryProvider`.
- **`learning_journey/` -> `ai_tutor/`**: `learningJourneyRepositoryProvider`
  watches `aiTutorRepositoryProvider`; `dailyLearningPlanProvider`
  watches `tutorSuggestionsProvider` (bypass — §2.3).
- **`smart_learning/` -> `learning_journey/`**: `smartLearningRepositoryProvider`
  watches `learningJourneyRepositoryProvider`.
- **`read_model/` -> `smart_learning/`**: `learningSnapshotRepositoryProvider`
  watches `smartLearningRepositoryProvider`; `learningSnapshotProvider`
  watches `smartLearningSessionProvider` (bypass — §2.3).
- **`analytics/` -> `learning/`, `flashcards/`, `lexicon/`, `stats/`**:
  `analyticsRepositoryProvider` watches `schedulerRepositoryProvider`,
  `flashcardRepositoryProvider`, `lexiconRepositoryProvider`,
  `studySessionRepositoryProvider`.
- **`flashcards/` -> `learning/`**: `flashcardSchedulerSyncProvider` and
  `dueFlashcardCardsProvider`/`lemmaCardsByIdProvider` watch
  `schedulerRepositoryProvider` (sync bridge, §2.4).
  `flashcard_review_screen.dart` also imports
  `learning/data/scheduler_providers.dart` directly.
- **`flashcards/` -> `lexicon/`**: `resolvedFlashcardsProvider`,
  `smartDeckFlashcardsProvider`, `verbFormGroupsProvider` all watch
  `lexiconRepositoryProvider`; `flashcard_review_providers.dart`
  (presentation) also watches `lexiconRepositoryProvider` directly,
  plus `add_flashcard_screen.dart` imports it for lemma search. Yes —
  flashcards/ consumes providers from both learning/ and lexicon/.
- **`learning/` -> `quran/`**: `schedulerSyncProvider` watches
  `userContentRepositoryProvider` (sync bridge, §2.4);
  `review_session_providers.dart` watches `quranRepositoryProvider`
  (to resolve ayah content for the current review item) and
  `dueReviewCardsProvider` (its own feature).
- **`learning_session/` -> `flashcards/`, `learning/`, `quiz/`**:
  `learningSessionControllerProvider` watches
  `dueFlashcardCardsProvider` (flashcards), `dueReviewCardsProvider`
  (learning), `quizSessionControllerProvider` (quiz), plus its own
  `learningPlannerProvider`. `learning_session_screen.dart` (UI) also
  directly imports all three sibling feature provider files. Yes —
  learning_session/ consumes providers from flashcards/, learning/,
  and quiz/.
- **`quiz/` -> `quran/`**: `quizContentPoolProvider` watches
  `quranRepositoryProvider`.
- **`khatm/` -> `quran/`**: `active_khatm_card.dart` (khatm
  presentation widget) imports `quran/data/quran_providers.dart`
  alongside its own `khatm_cycle_providers.dart`.
- **`library/` -> `quran/`**: `libraryItemsProvider` (declared in
  `library/presentation/library_controller.dart`, not `data/` — a
  cross-repository join provider) watches both
  `userContentRepositoryProvider` and `quranRepositoryProvider`.
- **`study/` -> `library/`**: `revision_queue_screen.dart` declares no
  providers of its own but consumes
  `libraryItemsProvider(LibraryKind.review)` indirectly by reusing
  `LibraryTabView`.
- **`stats/` -> `stats/` (intra-feature)**: `dailyGoalProgressProvider`
  (in `daily_goal_providers.dart`) watches `todayStudySummaryProvider`
  (in `study_session_providers.dart`) and `dailyGoalStoreProvider` (in
  `daily_goal_store.dart`) — three separate files in the same feature,
  not a single `*_providers.dart`.
- **`home/` -> `quran/`, `stats/`**: `todaysVerseProvider` watches
  `quranRepositoryProvider`; `HomeScreen` itself also watches
  `statsStoreProvider`, `readingPositionStoreProvider`,
  `surahListProvider` (all `quran/`), `currentStreakProvider` and
  `dailyGoalProgressProvider` (all `stats/`).
- **`profile/` -> `app/`**: `ProfileScreen` watches
  `themeControllerProvider` and `localeControllerProvider`.
- **`quran/reading_screen.dart` -> `stats/`** (notable direct
  repository reach-through): the reading screen reads
  `studySessionRepositoryProvider` and `statsStoreProvider` **directly**
  to record reading time — it does not go through any stats-owned
  orchestration provider; the write-path lives entirely in the UI
  layer rather than behind a `stats/`-owned provider.
- **`quran/data/` -> `quran/presentation/` (intra-feature, unusual
  direction)**: `user_content_providers.dart` (data layer) imports
  `presentation/reading/reading_controller.dart` to watch
  `surahReadingProvider` inside `ayahAnnotationsProvider` — a data
  file depending on a presentation file, the one layering exception
  found in the codebase.
- **`stats/` -> `quran/` presentation, without going through a
  provider**: `stats_store.dart`'s `ayahsRead` getter reads

  `ReadingPositionStore.posKey(surahId)` (a static helper on a

  `readingPositionStoreProvider` — a key-format coupling between

- **`search/` — currently isolated**: declares nothing and consumes

  (`ayahSearchProvider`) is owned by and used inside `quran/`
  (`SurahListScreen`/`surah_list_controller.dart`), not by `search/`.

### 3.3 "I want to change X, which file do I touch, and who reads it" — worked examples

- **Change how due-card sorting/dedup works** → edit
  `selectDueCardsOrdered` in `learning/data/scheduler_providers.dart`.
  Read by: `dueReviewCardsProvider` (learning/) and
  `dueFlashcardCardsProvider` (flashcards/, calls the same helper) —
  so both the Review Session and Flashcard Review flows are affected
  together.
- **Change what counts as "SRS due"** → same file/function as above;
  downstream consumers: `currentReviewItemProvider` (learning/),
  `currentFlashcardReviewItemProvider` (flashcards/),
  `learningSessionControllerProvider` (learning_session/, via both
  due-count providers).
- **Change the SM-2 algorithm** → override
  `schedulingAlgorithmProvider` (learning/) — no other file needs to
  change; `schedulerRepositoryProvider` and everything above it in the
  chain is insulated by the interface.
- **Change Analytics' underlying data sources** →
  `analytics/data/analytics_providers.dart`'s
  `analyticsRepositoryProvider` constructor args; this transitively
  affects `ai_tutor/`, `learning_journey/`, `smart_learning/`,
  `read_model/` (the whole chain in §2.2), plus
  `progress_dashboard_screen.dart`.
- **Change the Learning Journey's daily plan logic** →
  `computeDailyLearningPlan` is called from **two** places that must
  stay in sync: `LearningJourneyRepositoryImpl.getDailyPlan()` (the
  "real" path, reachable via `learningJourneyRepositoryProvider`) and
  `dailyLearningPlanProvider`'s bypass in
  `learning_journey_providers.dart` — see §2.3.
- **Change the Read Model snapshot logic** → same dual-path caveat as
  above, for `computeLearningSnapshot` /
  `learningSnapshotRepositoryProvider` / `learningSnapshotProvider` in
  `read_model/data/learning_snapshot_providers.dart`.
