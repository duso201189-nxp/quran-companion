# G8 Split Plan

Analysis of commit `d4976b0` only. No application code modified, no
history rewritten, no branch merged or touched — every figure below
comes from read-only `git diff-tree`, `git show`, and `git archive`
against the commit as it already exists.

---

AI Tutor, Knowledge docs."* Measuring the actual tree finds **thirteen**
distinguishable slices — the commit message under-describes its own

## 2 — How they separate into independent release candidates

Two techniques established the boundaries, both applied directly to
the commit's own tree rather than assumed from directory names:

**Directory clustering** grouped files by `lib/features/<name>/`,
revealing eight candidate feature verticals plus a shared
infrastructure layer (`lib/core/`, `lib/shared/`).

**Import-level dependency extraction** then tested whether those eight
candidates actually reference each other. First pass used
`package:quran_companion/...` import matching and found zero
cross-references — which turned out to be a false negative, because
this codebase uses **relative imports** throughout
(`../../analytics/domain/...`), not package-absolute ones. Caught by
sampling one file (`ai_tutor_repository_impl.dart`) before trusting the
zero-result grep, then re-run correctly. The corrected pass found a
real, non-trivial dependency graph — seven of the eight features import
at least one other new feature; only Lexicon imports none.

This distinction matters for the release plan: **the eight feature
verticals are not eight independent PRs that can land in any order** —
they form a partial order, and getting it wrong means a PR that doesn't
compile against `main` at the point it's opened.

### The two axes of complexity, kept separate on purpose

**Axis one — dependency order among the eight features.** Real,
enforced by the Dart compiler: opening the Flashcards PR before Lexicon
merges means Flashcards won't build. This axis has one correct answer,
derived in `G8_FEATURE_MATRIX.md`'s dependency summary.

**Axis two — shared-file contention** (`lib/l10n/*`, `lib/app/router.dart`,
`lib/features/home/presentation/home_screen.dart`). Not a compile-time
dependency — a file that three different feature PRs all need to touch.
This doesn't force an order, but it does mean these PRs cannot be
developed in true isolation on separate long-lived branches without
merge conflicts; each PR's diff to these shared files should stay small
and additive (new keys, new route entries, new entry-point widgets) so
conflicts are mechanical to resolve rather than semantic.

## 3 — The one slice that isn't a "feature" at all

`lib/core/database/` deserves separate treatment from every other slice
here because it isn't a feature — it's a schema change, and this
project's own constitution (`PROJ-P-002`) requires an explicit
stop-and-ask review for exactly this class of change, independent of
how large or small the rest of the commit around it is. Measuring it
precisely mattered: the raw diff is 8,883 lines, which would make it
look like the single biggest change in the entire commit. **8,624 of
those lines are Drift-generated `.g.dart` output** — regenerated by
`build_runner`, never hand-authored, not meaningfully reviewable
line-by-line. The actual hand-written schema change is 259 lines across
four files. Reporting only the raw number would have made this slice
look far riskier than the number a human reviewer actually needs to
read; reporting only the hand-written number would understate how much
generated surface a `flutter analyze`/test run still has to compile and
pass against. Both are in `G8_FEATURE_MATRIX.md`, deliberately not
collapsed into one figure.

## 4 — What a clean split cannot fully achieve

Not every one of the 229 files sorts cleanly into one slice.
`lib/l10n/*`, `lib/app/router.dart`, and the two screen-integration
files (`home_screen.dart`, `study_screen.dart`) are touched by multiple
features and can't be extracted as their own standalone PR — an
"l10n keys" PR that adds strings nothing yet references is dead weight,
and a "router" PR that registers routes to screens that don't exist yet
won't compile. These are accounted for in the matrix as **distributed**
rather than forced into an artificial thirteenth bucket, and the
release sequence in `G8_RELEASE_SEQUENCE.md` treats each feature PR as
implicitly carrying its own small slice of these shared files.

## 5 — Consistency with `RELEASE_INVENTORY.md`

`RELEASE_INVENTORY.md` classified all of G8 as a single "Requires
Commit Split" entry, correctly identifying the need for this work
without prescribing its shape. This document is that prescription. It
does not revise `RELEASE_INVENTORY.md`'s classification — G8 still
requires a split before merge — it resolves the *how*.
